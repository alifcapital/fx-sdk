## Overview

Forex (FX) trading SDK for partners. Provides gRPC client/server interfaces for order management and currency pair queries. The Go code in `go/forexv1/` is **generated from Protocol Buffer definitions** — do not edit those files by hand.

- Module path: `github.com/alifcapital/fx-sdk/go`
- Go version: 1.26.5
- Core dependencies: `google.golang.org/grpc`, `google.golang.org/protobuf`

## Architecture

### gRPC Services (package `forexv1`)

**OrderService** — forex order lifecycle:
- `SubmitOrder` — place an order (supports idempotency via `ref_id`); limit or market via `order_type`
- `CancelOrder` — cancel an existing order
- `GetOrderBookDepth` — market depth (bids/asks)
- `FilterClientOrders` — query orders with filters, pagination (limit/offset)
- `SubscribeOrderEvents` — server-streaming real-time order events

**PartnerService** — reference data:
- `GetCurrencyPairs` — available trading pairs and their specifications (`nbt_rate`, min lot, valid-rate band)

**TradeService** — trade settlement:
- `Trade` — bidirectional stream of executed trades; the client acks each one after storing it durably

### Package Layout

- `go/forexv1/` — generated protobuf + gRPC code (source protos: `forex/v1/order.proto`, `forex/v1/partner.proto`, `forex/v1/trade.proto`). Generated by `protoc-gen-go v1.36.12` / `protoc-gen-go-grpc v1.6.1`.
- `go/v1/` — hand-written client wrappers over the generated code: `client.go` (dial,
  metadata, options), `order.go`, `partner.go`, `trade.go` (settlement flow and
  `RetryUnsettled`), `retry.go` (backoff, stream reconnect), `types.go` (SDK-level
  types and sentinel errors).
- `go/pkg/` — small shared helpers (`fee.go`: percentage math on decimals).
- `go/db.sql` — schema for the partner-local PostgreSQL/TimescaleDB tables the SDK
  reads and writes (`client_orders`, `client_trades`, `reconciliations`).
- `go/example/main.go` — runnable end-to-end example.

## Domain Conventions

- All financial values (quantities, rates, amounts) are **strings** for arbitrary decimal precision.
- Every operation is scoped to a `partner_id`.
- Client identification uses `partner_id` + `client_id` + `client_inn` (taxpayer ID).
- Market segments are int32: Retail, Corporate, Treasury.
- Order days use `YYYY-MM-DD` date strings.
- **The FX Core operates in UTC+05:00** (Tajikistan, no DST). Every date, hour
  and window bound is that offset's calendar date and wall clock — never the
  host's or the PostgreSQL session's. The Core is the authority, so the offset
  is fixed, not configurable. Go code takes it from `v1.TimeZone` /
  `v1.Today()` / `v1.PreviousHour()`; SQL anchors every `TIMESTAMPTZ` compared
  against a date, or rendered as text, with the `atTZ` constant
  (`AT TIME ZONE INTERVAL '+05:00'`). Use the `INTERVAL` form: Postgres reads
  `AT TIME ZONE '+05'` with the inverted POSIX sign convention, silently
  shifting the window ten hours. Getting this wrong makes every reconciliation
  hour diverge and files `order_day` on the wrong day around midnight.
- Order types are int32: 1 = limit (the default when unset), 2 = market. A market
  order carries no `limit_rate` (NULL in `client_orders`), its unfilled remainder
  is cancelled rather than rested, and its fill is reported synchronously in
  `SubmitOrderResponse.filled_quantity` / `average_rate`.
- `counterparty_segment` is a restriction, not a segment: 0 = any counterparty,
  3 = treasury only, and only a Treasury order may set it.
- Fills are only ever applied to `client_orders.remaining_quantity` by the trade
  stream, never by the synchronous submit response, so a market order's fill is
  not counted twice.
