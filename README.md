# Руководство разработчика по fx-sdk (Go)

SDK для интеграции партнёров с системой FX Core (форекс-торговля).
Предоставляет высокоуровневый gRPC-клиент для управления ордерами, получения
рыночных данных и обработки сделок (trades) с автоматическим учётом во
локальной базе данных партнёра.

- **Путь модуля:** `github.com/alifcapital/fx-sdk/go`
- **Рабочий пакет:** `github.com/alifcapital/fx-sdk/go/v1`

## Архитектура

SDK оборачивает три gRPC-сервиса FX Core и синхронизирует их состояние с
**локальной базой данных партнёра** (PostgreSQL / TimescaleDB):

| Сервис | Назначение |
|--------|-----------|
| `OrderService` | Жизненный цикл ордеров (отправка, отмена, стакан, фильтр, события) |
| `TradeService` | Поток исполненных сделок (двунаправленный стрим с подтверждением) |
| `PartnerService` | Справочные данные (валютные пары и их торговые характеристики) |

Ключевые особенности:

- **Локальный учёт.** Каждый ордер сначала записывается в таблицу `client_orders`,
  и только потом отправляется в Core. `ref_id` (идемпотентный ключ) генерируется
  базой как `BIGSERIAL`.
- **Идемпотентность.** SDK защищает от дублей: одинаковый ордер в пределах
  1 минуты отклоняется (`ErrDuplicateOrder`).
- **Надёжность стримов.** Подписки автоматически переподключаются с
  экспоненциальной задержкой (backoff) при временных сбоях.
- **Гарантия расчёта сделок.** Сделка сначала надёжно сохраняется в БД, затем
  подтверждается в Core (ack), и только потом выполняется расчёт по счетам
  партнёра. Незавершённые расчёты переигрываются через `RetryUnsettled`.
- **Десятичная точность.** Все денежные значения — это **строки** (`string`),
  чтобы избежать потери точности при работе с числами с плавающей точкой.

## Как работает SDK — все сценарии

### Три канала

| Канал | Что приходит | Что меняет в `client_orders` | Ваш обработчик |
|---|---|---|---|
| Ответ `SubmitOrder` | только **принят или нет**: `Pending`, `Rejected`, `Duplicate`, `Failed` | при отказе — статус; при приёме — только `order_id` | по исполнению — ничего; что делать с блокировкой при каждом исходе — см. [Что делать по ответу `SubmitOrder`](#что-делать-по-ответу-submitorder) |
| Стрим сделок `SubscribeTrades` | каждая сделка | остаток уменьшается, статус `FilledPartially` или `Filled` | `handleTrade` — **проводка денег** клиента |
| Стрим событий `SubscribeOrderEvents` | истёк, отменён Core, отменён остаток рыночного ордера | статус и остаток из Core | `handleOrderEvent` — **снять блокировку** (`GetReleaseAmount`) |
| Ответ `CancelOrder` | ордер отменён вами | статус и остаток из Core | снять блокировку по `CancelOrderResult.RemainingQuantity` |
| `ReconcileOrders` (раз в час) | всё, что потерялось в каналах выше | догружает сделки, закрывает ордера | те же `handleTrade` и `handleOrderEvent` |

Главное правило: **исполнение и закрытие ордера приходят только по стримам**. Ответ
`SubmitOrder` ничего не говорит о том, исполнился ли ордер, даже если он исполнился
мгновенно.

### Жизнь ордера: что и откуда приходит

| # | Сценарий | Ответ `SubmitOrder` | Потом по стримам | Итог в `client_orders` | Блокировка |
|---|---|---|---|---|---|
| 1 | Лимитный ордер встал в стакан | `Pending` | ничего (пока нет встречного) | `Pending` | держится |
| 2 | Лимитный ордер исполнился сразу полностью | `Pending` | сделки | `Filled`, остаток 0 | снимать нечего |
| 3 | Исполнился сразу частично, остаток в стакане | `Pending` | сделки | `FilledPartially` | держится на остаток |
| 4 | Стоял в стакане, потом исполнили встречным ордером | — | сделки | `FilledPartially` → `Filled` | — |
| 5 | Вы отменили (`CancelOrder`) | — | — | `Cancelled` / `CancelledPartially` из ответа `CancelOrder` | снять по ответу `CancelOrder` |
| 6 | Истёк срок (Retail 24 ч, Corporate/Treasury в 18:00) | — | событие `Expired` / `ExpiredPartially` | статус и остаток из события | снять по событию |
| 7 | Core отменил (партнёр отключён) | — | событие `Cancelled` / `CancelledPartially` | статус и остаток из события | снять по событию |
| 8 | Рыночный ордер исполнился полностью | `Pending` | сделки | `Filled` | снимать нечего |
| 9 | Рыночный ордер исполнился частично | `Pending` | сделки + событие `CancelledPartially` (остаток отменён) | `CancelledPartially`, остаток = отменённый | снять по событию |
| 10 | Рыночный ордер, стакан пуст | `Pending` | событие `Cancelled` | `Cancelled`, остаток = весь объём | снять по событию |
| 11 | Отклонён проверкой (курс, шаг, лимиты…) | `Rejected` + `Cause` | ничего | `Rejected` | снять сразу |
| 12 | Тот же ордер уже был отправлен меньше минуты назад | `ErrDuplicateOrder` (SDK, ордер не отправлен) | ничего | без изменений | держать — первый ордер в работе |
| 13 | Повтор запроса после обрыва связи, первый дошёл | `Duplicate` (Core) | как у исходного ордера | `Pending`, `order_id` проставит сверка | держать — ордер принят |
| 14 | Не удалось поставить в стакан | `Failed` | ничего | `Failed` | снять сразу |
| 15 | Ошибка связи, неизвестно, дошёл ли ордер | ошибка `Unavailable` / тайм-аут | если дошёл — как обычно | `Pending` без `order_id` | держать; если не дошёл — снимет `ReconcileOrders` |

### Порядок прихода не важен

Сделки и события идут разными стримами, и порядок их прихода не гарантирован. SDK
устроен так, что результат один и тот же:

- сделка ставит только `FilledPartially` или `Filled`; закрывающие статусы
  (истёк, отменён) приходят только событием;
- если ордер у вас **уже закрыт**, сделка сохраняется и проводится, но статус и
  остаток ордера не трогает — они уже из Core
  (подробнее — [Сделка не меняет закрытый ордер](#сделка-не-меняет-закрытый-ордер)).

### Если что-то потерялось

Сделка и событие отправляются **один раз** и только в открытый стрим. Если стрим был
оборван (рестарт приложения, деплой Core, сеть), сообщение теряется — его
восстанавливает [`ReconcileOrders`](#сверка-с-core--reconcileorders):

| Что потерялось | Как это выглядит у вас | Что делает сверка |
|---|---|---|
| Событие (истёк / отменён) | ордер «живой», хотя срок прошёл | закрывает статусом Core, вызывает `handleOrderEvent` |
| Сделки живого ордера | остаток больше, чем в Core | догружает сделки, вызывает `handleTrade` |
| Сделки, а событие дошло | ордер закрыт, но сделок меньше, чем исполнено | догружает сделки, блокировку **не** снимает (сняло событие) |
| И сделки, и событие | ордер «живой», сделок нет | догружает сделки, закрывает ордер, снимает блокировку |
| Ответ `SubmitOrder` (сеть) | ордер `Pending` без `order_id` | ставит `order_id` и статус из Core |
| Сам ордер не дошёл до Core | ордер `Pending`, в Core его нет | ставит `Failed`, снимает блокировку |

Сверка проверяет ордера, поданные больше 25 часов назад, поэтому восстановление
приходит с задержкой; в обычной работе всё приходит сразу по стримам. Полная таблица
случаев — в разделе [Сверка с Core — ReconcileOrders](#сверка-с-core--reconcileorders).

### Что обязательно сделать в приложении

1. Держать открытыми **оба** стрима — `SubscribeTrades` и `SubscribeOrderEvents`.
2. `handleTrade` — проводка денег; **идемпотентный** (одна сделка может прийти
   повторно: после переподключения, через `RetryUnsettled`, через сверку).
3. `handleOrderEvent` — снятие блокировки по `GetReleaseAmount()`.
4. Не считать ордер исполненным и не снимать блокировку по ответу `SubmitOrder`.
5. Запускать `RetryUnsettled` и `ReconcileOrders` при старте и по таймеру
   (см. [полный пример](#полный-пример)).

## Предварительные требования: база данных

SDK хранит ордера и сделки в **локальной БД партнёра**. Перед использованием
необходимо создать таблицы. Полная схема находится в файле [`go/db.sql`](go/db.sql).

Требуется **PostgreSQL с расширением TimescaleDB** (таблицы создаются как
гипертаблицы с партиционированием по дню).

Основные таблицы:

- `client_orders` — все отправленные ордера. Первичный ключ `(ref_id, order_day)`.
- `client_trades` — исполненные сделки. Первичный ключ `(trade_id, order_id, trading_day)`.

Создание схемы:

```bash
psql "postgres://user:pass@host:5432/fxdb" -f go/db.sql
```

> **Важно:** SDK выполняет SQL-запросы напрямую к этим таблицам. Имена и
> структура колонок менять нельзя.

## Часовой пояс — UTC+05:00

**FX Core работает в UTC+05:00** (время Таджикистана, перехода на летнее время
нет). Все даты и часы, которые Core присылает, ожидает и сравнивает, заданы в
этом смещении, поэтому SDK привязан к нему же. Это относится к `order_day`,
`trading_day` и к границам окна у `GetTrades`.

Смещение задано жёстко и не настраивается: его определяет Core, а не партнёр.

**Часовой пояс сессии PostgreSQL и часовой пояс хоста не имеют значения.** SDK
не полагается на настройку `TimeZone`: каждое сравнение `TIMESTAMPTZ` с датой
привязывается к смещению явно, через `AT TIME ZONE INTERVAL '+05:00'`.
Настраивать пул подключений не нужно.

### Почему это важно

Если дата берётся из сессии, ломается **`order_day` около полуночи.** Колонка входит в первичный ключ
   `client_orders` и является тем значением, по которому сделка связывается со
   своим ордером. В 02:30 по +05 сессия в UTC записала бы предыдущий день
   (21:30), после чего Core не нашёл бы ордер по `order_day`.

### Ловушка со знаком

В SQL используйте форму `INTERVAL`, а не строку. PostgreSQL трактует
`AT TIME ZONE '+05'` по инвертированному соглашению POSIX:

```sql
SELECT TIMESTAMP '2026-04-30 10:00:00' AT TIME ZONE '+05';               -- 15:00Z — неверно
SELECT TIMESTAMP '2026-04-30 10:00:00' AT TIME ZONE INTERVAL '+05:00';   -- 05:00Z — верно
SELECT TIMESTAMP '2026-04-30 10:00:00' AT TIME ZONE 'Asia/Dushanbe';     -- 05:00Z — верно
```

Ошибка в знаке сдвигает время на десять часов и ничем себя не проявляет.

### Что использовать в своём коде

Не берите день и час из `time.Now()` — часы хоста могут идти в другом поясе:

```go
// Текущий торговый день в поясе SDK.
day := v1.Today()

// Последний ЗАВЕРШЁННЫЙ час. Корректно переходит через полночь:
// в 00:30 пятого числа вернёт час 23 четвёртого.
prevDay, hour := v1.PreviousHour()

// Если нужен свой расчёт — используйте пояс SDK, а не time.Local.
t := time.Now().In(v1.TimeZone)
```

| Идентификатор     | Назначение                                                   |
| ----------------- | ------------------------------------------------------------ |
| `v1.TimeZone`     | Фиксированный пояс UTC+05:00 (`*time.Location`)              |
| `v1.Today()`      | Текущий торговый день в этом поясе, `YYYY-MM-DD`             |
| `v1.PreviousHour()` | День и час последнего завершённого часа                    |

В собственных запросах к `client_orders` и `client_trades` привязывайте
`TIMESTAMPTZ` так же, как это делает SDK, иначе ваши отчёты не совпадут с
данными Core:

```sql
-- сделки за час 10 по +05
SELECT *
  FROM client_trades
 WHERE trading_day = '2026-04-30'::date
   AND executed_at >= TIMESTAMP '2026-04-30 10:00:00' AT TIME ZONE INTERVAL '+05:00'
   AND executed_at <  TIMESTAMP '2026-04-30 11:00:00' AT TIME ZONE INTERVAL '+05:00';

-- вывод времени в поясе SDK, а не сессии
SELECT to_char(executed_at AT TIME ZONE INTERVAL '+05:00', 'YYYY-MM-DD HH24:MI:SS')
  FROM client_trades;
```

Колонки времени остаются `TIMESTAMPTZ` и хранят однозначный момент времени —
привязка влияет только на то, к какому календарному дню и к какому часу этот
момент отнесён.

## Создание клиента

Клиент создаётся функцией `v1.New`. Она требует адрес Core, идентификатор SDK,
API-ключ, идентификатор партнёра и пул соединений с локальной БД (`*pgxpool.Pool`).

```go
import (
    "context"
    "time"

    "github.com/jackc/pgx/v5/pgxpool"
    "google.golang.org/grpc"
    "google.golang.org/grpc/credentials/insecure"

    v1 "github.com/alifcapital/fx-sdk/go/v1"
)

func newClient(ctx context.Context) (*v1.Client, error) {
    // Пул соединений с локальной БД партнёра.
    pool, err := pgxpool.New(ctx, "postgres://user:pass@localhost:5432/fxdb?sslmode=disable")
    if err != nil {
        return nil, err
    }

    opts := []v1.Option{
        v1.WithMaxRetries(3),
        v1.WithRetryBackoff(100*time.Millisecond, 5*time.Second),
        // DEV: незащищённое (plaintext) соединение — только для разработки.
        // PROD: используйте mTLS — см. раздел «Транспорт и безопасность».
        v1.WithDialOptions(
            grpc.WithTransportCredentials(insecure.NewCredentials()),
        ),
    }

    client, err := v1.New(
        "fx-core.example.com:443", // адрес Core
        "019eee39-cc7f-722e-a3f1-c2c010b141a4", // sdk_id (ровно 36 символов, UUID)
        "ВАШ_API_КЛЮЧ",                          // api_key
        "019eee2d-d765-7273-8582-ab6982339896",  // partner_id
        pool,
        opts...,
    )
    if err != nil {
        return nil, err
    }
    return client, nil
}
```

Параметры `New(target, sdkId, apiKey, partnerId, db, opts...)`:

| Параметр | Описание | Валидация |
|----------|----------|-----------|
| `target` | Адрес gRPC-сервера Core | не пустой |
| `sdkId` | Идентификатор SDK | строго 36 символов (UUID) |
| `apiKey` | API-ключ партнёра | не пустой |
| `partnerId` | Идентификатор партнёра | не проверяется при создании; пустое значение отклонят вызовы |
| `db` | Пул соединений `*pgxpool.Pool` | не `nil` |

`sdkId`, `apiKey` и `partnerId` автоматически добавляются в gRPC-метаданные
(`key-id`, `api-key`, `partner-id`) каждого запроса.

`partnerId` - идентификатор партнёра для каждого запроса.

> Не забудьте вызвать `defer client.Close()` для освобождения соединения.

## Транспорт и безопасность (TLS / mTLS)

Тип транспорта задаётся через `WithDialOptions` и **различается между окружениями**:

| Окружение | Транспорт | Учётные данные |
|-----------|-----------|----------------|
| **DEV** (разработка) | Незащищённый (plaintext), без mTLS | `insecure.NewCredentials()` |
| **PROD** (продакшен) | **mTLS** (взаимная аутентификация по сертификатам) | клиентский сертификат + ключ + CA |

### DEV — без mTLS

В среде разработки Core принимает незащищённое (plaintext) соединение:

```go
import "google.golang.org/grpc/credentials/insecure"

opts := []v1.Option{
    v1.WithDialOptions(
        grpc.WithTransportCredentials(insecure.NewCredentials()),
    ),
}
```

> Используйте `insecure` **только** в разработке. Никогда не подключайтесь к
> продакшену без TLS — API-ключ уйдёт по сети в открытом виде.

### PROD — mTLS

В продакшене Core требует **взаимный TLS (mTLS)**: помимо проверки сертификата
сервера, клиент обязан предъявить собственный сертификат, подписанный доверенным
CA. Партнёр получает клиентский сертификат (`client.crt`), приватный ключ
(`client.key`) и корневой сертификат CA (`ca.crt`).

```go
import (
    "crypto/tls"
    "crypto/x509"
    "fmt"
    "os"

    "google.golang.org/grpc"
    "google.golang.org/grpc/credentials"

    v1 "github.com/alifcapital/fx-sdk/go/v1"
)

func mtlsDialOption(certFile, keyFile, caFile, serverName string) (grpc.DialOption, error) {
    // Клиентская пара сертификат/ключ — её предъявляем серверу.
    cert, err := tls.LoadX509KeyPair(certFile, keyFile)
    if err != nil {
        return nil, fmt.Errorf("загрузка клиентского сертификата: %w", err)
    }

    // CA, которым подписан сертификат сервера, — для проверки сервера.
    caPEM, err := os.ReadFile(caFile)
    if err != nil {
        return nil, fmt.Errorf("чтение CA: %w", err)
    }
    pool := x509.NewCertPool()
    if !pool.AppendCertsFromPEM(caPEM) {
        return nil, fmt.Errorf("не удалось разобрать CA-сертификат")
    }

    tlsCfg := &tls.Config{
        Certificates: []tls.Certificate{cert}, // mTLS: предъявляем свой сертификат
        RootCAs:      pool,                     // проверяем сертификат сервера
        ServerName:   serverName,               // должен совпадать с CN/SAN сервера
        MinVersion:   tls.VersionTLS12,
    }
    return grpc.WithTransportCredentials(credentials.NewTLS(tlsCfg)), nil
}
```

Использование при создании клиента:

```go
dialOpt, err := mtlsDialOption(
    "/etc/fx-sdk/client.crt",
    "/etc/fx-sdk/client.key",
    "/etc/fx-sdk/ca.crt",
    "fx-core.example.com", // имя из сертификата сервера
)
if err != nil {
    log.Fatalf("настройка mTLS: %v", err)
}

opts := []v1.Option{
    v1.WithMaxRetries(3),
    v1.WithRetryBackoff(100*time.Millisecond, 5*time.Second),
    v1.WithDialOptions(dialOpt),
}

client, err := v1.New(
    "fx-core.example.com:443",
    sdkID, apiKey, partnerID, pool,
    opts...,
)
```

Рекомендации для продакшена:

- Храните `client.key` с правами `0600`, вне репозитория (секрет-хранилище).
- `ServerName` должен совпадать с CN/SAN в сертификате сервера, иначе рукопожатие
  (handshake) не пройдёт.
- Отслеживайте срок действия сертификатов и обновляйте их заранее.
- Не используйте `InsecureSkipVerify: true` — это отключает проверку сервера и
  сводит на нет смысл mTLS.

## Параметры конфигурации

Опции передаются в `v1.New` через вариативный аргумент `opts ...Option`:

| Опция | Назначение | Значение по умолчанию |
|-------|-----------|----------------------|
| `WithMaxRetries(n int)` | Кол-во повторов для временных ошибок gRPC (`Unavailable`, `ResourceExhausted`) | 3 |
| `WithRetryBackoff(base, max time.Duration)` | Базовая и максимальная задержка экспоненциального backoff | 100ms / 5s |
| `WithDialOptions(opts ...grpc.DialOption)` | Дополнительные опции подключения gRPC (например, TLS) | — |

Backoff применяется как к unary-вызовам, так и к переподключению стримов.
Для долгоживущих стримов SDK также включает gRPC keepalive (пинг каждые 30 секунд),
чтобы прокси и NAT не разрывали простаивающее соединение.

## Отправка ордера — SubmitOrder

Размещает новый ордер. SDK сначала вставляет строку в `client_orders`
(генерируя `ref_id` и `order_day`), затем отправляет ордер в Core и обновляет
локальную строку статусом из ответа.

```go
acc := map[string]string{
    "debit_account":  "1271",
    "credit_account": "4571",
}
fee := map[string]string{
    "fixed": "0.05", // комиссия в процентах (0.05%)
}

res, err := client.SubmitOrder(ctx, &v1.SubmitOrderParams{
    Side:             v1.Buy,        // Buy или Sell
    Segment:          v1.Retail,     // Retail / Corporate / Treasury
    PartnerId:        partnerId,
    ClientId:         "1271",
    ClientINN:        "071283210",   // ИНН клиента: от 9 до 12 цифр
    CurrencyPair:     "USD/TJS",
    Quantity:         "1000.00",     // десятичная строка
    LimitRate:        "9.31",        // десятичная строка (обязателен для лимитного ордера)
    MinTradeQuantity: "100.00",      // мин. объём одной сделки; пусто — минимум валютной пары
    Account:          acc,           // произвольный JSONB
    Fee:              fee,           // произвольный JSONB
    OrderType:        v1.LimitOrder, // 0 или v1.LimitOrder — лимитный; v1.MarketOrder — рыночный
})
if err != nil {
    if errors.Is(err, v1.ErrDuplicateOrder) {
        log.Println("дубликат ордера в пределах 1 минуты — пропускаем")
        return
    }
    log.Fatalf("ошибка отправки ордера: %v", err)
}

log.Printf("ref_id=%d order_id=%d order_day=%s status=%d cause=%q",
    res.RefId, res.OrderId, res.OrderDay, res.Status, res.Cause)
```

**Обязательные поля:** `ClientId`, `PartnerId`, `Segment` (должен быть в диапазоне
`Retail..Treasury`), `LimitRate` — **только для лимитного ордера**.

**Что проверяет Core.** Эти правила SDK не дублирует: ордер уходит в Core и
возвращается со статусом `Rejected` и причиной в `Cause`.

| Поле | Правило | `Cause` при нарушении |
|------|---------|-----------------------|
| `ClientId` | от 1 до 100 символов (пробелы по краям обрезаются) | `clientId: от 1 до 100 символов` |
| `ClientINN` | от 9 до 12 цифр `0–9`, без пробелов и букв | `clientInn: от 9 до 12 цифр` |
| `Quantity` | не больше 10¹⁵ | `quantity превышает максимально допустимое значение` |
| `Quantity × курс` | не больше 10¹⁵ | `сумма ордера (quantity × курс) превышает максимально допустимое значение` |
| `LimitRate` | кратен шагу курса пары `TickSize` (см. [GetCurrencyPairs](#валютные-пары--getcurrencypairs)) | `limitRate должен быть кратен шагу курса 0.01` |

Предел 10¹⁵ — технический потолок, а не торговый лимит: он на порядки выше
любой реальной сделки в любой валюте. Для рыночного ордера в произведение идёт
граница курсового коридора пары, а не `LimitRate`.

Шаг курса проверяется только у лимитного ордера: при шаге `0.01` курс `9.99`
принимается, а `9.9999` отклоняется. Курс рыночного ордера Core сам округляет до
шага внутрь коридора, поэтому рыночный ордер по шагу не отклоняется.

> **Точность десятичных:** `Quantity`, `LimitRate` и `MinTradeQuantity` несут не
> более **6 знаков после запятой** — столько хранят и SDK, и Core. Значение с
> большей точностью отклоняется с `v1.ErrDecimalPrecision` ещё до записи в
> локальную БД и до отправки в Core, а не округляется молча: сумма, под которую
> партнёр зарезервировал средства, должна совпадать с суммой сделки. Хвостовые
> нули точностью не считаются — `"1000.1000000"` принимается.

**Результат `SubmitOrderResult`:**

| Поле | Описание |
|------|----------|
| `RefId` | Локальный идемпотентный ключ (используется для отмены и сопоставления) |
| `OrderId` | Идентификатор ордера в Core — его принимает `CancelOrder`; `0`, если Core отклонил ордер до сохранения. Также записывается в `client_orders.order_id` |
| `OrderDay` | Дата ордера в формате `YYYY-MM-DD` |
| `Status` | Принят ли ордер: `Pending` — принят; `Rejected` — отклонён (причина в `Cause`); `Duplicate`; `Failed` — не удалось поставить в стакан |
| `Cause` | Причина отклонения/ошибки, если есть |

> **Ответ говорит только «принят или нет».** Исполнение в ответ не приходит
> никогда — даже если ордер исполнился мгновенно. Всё, что с ордером происходит
> после приёма, приходит **только по стримам**:
>
> - сделки — в `SubscribeTrades` (обработчик `handleTrade`), они меняют
>   статус и остаток ордера;
> - истечение, отмена Core, отменённый остаток рыночного ордера — событием в
>   `SubscribeOrderEvents` (обработчик `handleOrderEvent`).
>
> Если что-то из этого потерялось (стрим был оборван), это восстановит
> [`ReconcileOrders`](#сверка-с-core--reconcileorders). Поэтому не считайте ордер
> исполненным по ответу `SubmitOrder` и не снимайте по нему блокировку.

> **Защита от дублей:** если ордер с теми же `side`, `limit_rate`, `quantity`,
> `currency_pair`, `order_type`, `partner_id`, `client_id` был отправлен за
> последнюю минуту, возвращается `v1.ErrDuplicateOrder`.

### Что делать по ответу `SubmitOrder`

Приложение обычно **блокирует средства клиента до вызова** `SubmitOrder`. Что делать
с этой блокировкой, зависит от исхода:

| Исход | Что это значит | Ордер в Core | `client_orders` | Что делать |
|---|---|---|---|---|
| `Status = Pending` | ордер **принят** | есть | `Pending`, записан `order_id` | **держать** блокировку; ждать сделок (`handleTrade`) и событий (`handleOrderEvent`) |
| `Status = Rejected` | ордер **отклонён проверкой** Core: курс вне коридора, не кратен шагу, объём меньше минимума, неактивная пара, нет реквизитов… | **нет** | `Rejected`, `cause` = причина | **снять** блокировку; показать клиенту `Cause` (текст на русском, для показа как есть); после исправления подать **новый** ордер |
| `Status = Failed` | Core сохранил ордер, но не смог поставить его в стакан (сбой на стороне Core) | есть, `Failed` | `Failed`, `cause` = причина | **снять** блокировку; можно подать **новый** ордер; это ошибка Core — сообщить в поддержку FX |
| `Status = Duplicate` | Core **уже получил этот ордер** (тот же `ref_id`): обычно SDK повторил запрос после обрыва связи, а первый запрос успел дойти | есть — исходный ордер | `Pending`, без `order_id` | считать ордер **принятым**: **держать** блокировку, **не** подавать заново; исполнение придёт по стримам, `order_id` и статус проставит `ReconcileOrders` |
| `err == v1.ErrDuplicateOrder` | **SDK сам** не отправил ордер: такой же (сторона, курс, объём, пара, клиент) отправлялся меньше минуты назад | не отправлялся | новой строки нет | ничего не снимать и не повторять — первый ордер уже в работе; если клиент действительно хочет второй такой же, подать его позже |
| `err` — ошибка проверки SDK (`ErrDecimalPrecision`, `ErrLimitRateRequired`, `ErrClientIDRequired`, …) | ордер не прошёл проверку **до отправки** | не отправлялся | новой строки нет | **снять** блокировку; исправить параметры |
| `err` — ошибка связи после повторов (`Unavailable`, тайм-аут) | **неизвестно**, дошёл ли ордер до Core | может быть, а может не быть | `Pending`, без `order_id` | **не снимать** блокировку и **не подавать заново** — иначе можно получить два ордера. Если ордер дошёл, по стримам придут сделки и события. Если не дошёл, `ReconcileOrders` через 25 ч поставит `Failed` («ордер не дошёл до Core») и вызовет `handleOrderEvent`, где блокировка снимется |

Как отличить «ошибку связи» от остальных ошибок: ошибки проверки SDK сравниваются через
`errors.Is` с переменными `v1.Err…`; ошибка связи приходит из gRPC (`status.Code(err)` —
`Unavailable`, `DeadlineExceeded`) с префиксом `fx-sdk: submit order:`.

> **Редкий случай с `Failed`.** Если у Core одновременно не сработали и стакан, и база,
> ответ может прийти `Failed`, а ордер позже всё же исполнится. Тогда по нему придут
> сделки, и `handleTrade` будет вызван для ордера, который вы считали несостоявшимся.
> `handleTrade` должен провести сделку **всегда**, даже если блокировка по ордеру уже
> снята: сделка — это факт, деньги по ней должны двигаться.

### Тип ордера — лимитный и рыночный

| `OrderType` | Цена | Неисполненный остаток |
|-------------|------|-----------------------|
| `v1.LimitOrder` (1, по умолчанию) | `LimitRate` или лучше | остаётся в стакане до исполнения, истечения срока или отмены |
| `v1.MarketOrder` (2) | лучшие доступные цены стакана | **отменяется**, в стакане ничего не остаётся |

Рыночный ордер **игнорирует `LimitRate`** — SDK не отправляет это поле в Core и
записывает в `client_orders.limit_rate` значение `NULL`. Как и для лимитного
ордера, ответ означает только «принят»; что исполнилось и по какому курсу,
приходит сделками, а отменённый остаток — событием ордера:

```go
res, err := client.SubmitOrder(ctx, &v1.SubmitOrderParams{
    Side:             v1.Buy,
    Segment:          v1.Retail,
    PartnerId:        partnerId,
    ClientId:         "1271",
    ClientINN:        "071283210",
    CurrencyPair:     "USD/TJS",
    Quantity:         "100.00",
    OrderType:        v1.MarketOrder, // LimitRate не указывается
    Account:          acc,
    Fee:              fee,
})
if err != nil {
    log.Fatalf("ошибка отправки рыночного ордера: %v", err)
}

log.Printf("рыночный ордер принят: ref_id=%d статус=%d", res.RefId, res.Status)
```

Дальше по этому ордеру придут:

| Что | Где | Пример |
|---|---|---|
| Каждая сделка | `handleTrade` | 40 по 10.95, затем 30 по 10.96 |
| Отменённый остаток | `handleOrderEvent`, `EventType = CancelledPartially` (или `Cancelled`, если не исполнилось ничего), `RemainingQuantity` — сколько отменено | остаток 30 — снять блокировку на 30 |

Средний курс считайте по сделкам: Σ(объём × курс) / Σ объём.

### Ограничение контрагента — `CounterpartySegment`

По умолчанию (`v1.AnyCounterparty`, значение `0`) ордер может встретиться с
контрагентом из любого сегмента. Ордер сегмента `Treasury` может дополнительно
потребовать сводить его **только с казначейскими контрагентами**:

```go
res, err := client.SubmitOrder(ctx, &v1.SubmitOrderParams{
    Segment:             v1.Treasury,
    CounterpartySegment: v1.Treasury, // только казначейские контрагенты
    // ... остальные поля
})
```

Любое другое значение отклоняется с `v1.ErrInvalidCounterpartySegment`, а попытка
задать `Treasury` для ордера другого сегмента — с `v1.ErrTreasuryCounterpartyOnly`.

## Отмена ордера — CancelOrder

Отменяет существующий ордер. Требует `OrderId` и `OrderDay`.

`OrderId` — это идентификатор ордера **в Core**, а не локальный `RefId`.
Его возвращает `SubmitOrder` (`SubmitOrderResult.OrderId`) и SDK сохраняет его в
`client_orders.order_id`. Также его можно получить из
[`FilterClientOrders`](#фильтрация-ордеров--filterclientorders) (`Order.OrderId`)
или из события сделки (`TradeEvent.OrderId`).

```go
open, err := client.FilterClientOrders(ctx, &v1.FilterClientOrdersParams{
    PartnerId: partnerId,
    ClientId:  "1271",
    Status:    v1.Pending,
    Limit:     50,
})
if err != nil || len(open.Orders) == 0 {
    log.Fatalf("нет открытых ордеров: %v", err)
}
target := open.Orders[0] // клиент выбирает, какой ордер отменить

res, err := client.CancelOrder(ctx, &v1.CancelOrderParams{
    PartnerId: partnerId,
    ClientId:  "1271",
    OrderId:   target.OrderId, // order_id из Core
    OrderDay:  target.OrderDay,
})
if err != nil {
    log.Fatalf("ошибка отмены: %v", err)
}

log.Printf("success=%v remaining=%s status=%d cause=%q",
    res.Success, res.RemainingQuantity, res.Status, res.Cause)
```

**Результат `CancelOrderResult`:**

| Поле | Описание |
|------|----------|
| `Success` | Успешно ли отменён ордер |
| `RemainingQuantity` | Невыполненный объём на момент отмены (для возврата средств) |
| `Status` | Обновлённый статус ордера |
| `Cause` | Причина неудачи, если есть |
| `RefId` | Локальный `ref_id`, связанный с ордером |

При успешной отмене SDK автоматически обновляет статус и остаток в `client_orders`.

## Фильтрация ордеров — FilterClientOrders

Запрашивает у Core ордера клиента по фильтрам с пагинацией.

```go
res, err := client.FilterClientOrders(ctx, &v1.FilterClientOrdersParams{
    PartnerId:    partnerId,
    ClientId:     "1271",          // обязательно
    RefId:        0,               // опционально (0 = не задано)
    CurrencyPair: "USD/TJS",       // опционально
    Side:         v1.Buy,          // опционально (0 = не задано)
    Status:       v1.Pending,      // опционально (0 = не задано)
    OrderDayFrom: "2026-06-01",    // YYYY-MM-DD; по умолчанию сегодня
    OrderDayTo:   "2026-06-30",    // YYYY-MM-DD; по умолчанию сегодня+1
    Limit:        50,              // максимум 100
    Offset:       0,
})
if err != nil {
    log.Fatalf("ошибка фильтра: %v", err)
}

for _, o := range res.Orders {
    log.Printf("order_id=%d day=%s side=%d status=%d type=%d counterparty=%d qty=%s remaining=%s rate=%s ref=%d expires=%s",
        o.OrderId, o.OrderDay, o.Side, o.Status, o.OrderType, o.CounterpartySegment,
        o.Quantity, o.RemainingQuantity, o.LimitRate, o.RefId, o.ExpiresAt)
}
```

**Обязательные поля:** `ClientId`, `PartnerId`.

Если `OrderDayFrom` или `OrderDayTo` пусты, SDK подставляет сегодня и сегодня+1
соответственно. Каждый элемент `res.Orders` имеет тип `v1.Order`
(см. [справочник типов](#справочник-типов-и-констант)).

## Стакан цен — GetOrderBookDepth

Возвращает агрегированный стакан (заявки на покупку `Bids` и на продажу `Asks`)
для валютной пары.

```go
depth, err := client.GetOrderBookDepth(ctx, &v1.GetOrderBookDepthParams{
    Segment:      v1.Retail,
    MaxLevels:    10,          // максимальное число ценовых уровней
    ClientId:     "1271",
    CurrencyPair: "USD/TJS",
    PartnerId:    partnerId,
})
if err != nil {
    log.Fatalf("ошибка стакана: %v", err)
}

log.Println("Asks (продажа):")
for i := len(depth.Asks) - 1; i >= 0; i-- {
    log.Printf("  %s: %s", depth.Asks[i].Rate, depth.Asks[i].TotalQuantity)
}
log.Println("Bids (покупка):")
for _, b := range depth.Bids {
    log.Printf("  %s: %s", b.Rate, b.TotalQuantity)
}
```

Каждый уровень `v1.PriceLevel` содержит `Rate` (цена) и `TotalQuantity`
(суммарный объём), обе — десятичные строки.

**Обязательные поля:** `ClientId`, `PartnerId`, корректный `Segment`.

## Валютные пары — GetCurrencyPairs

Возвращает список доступных для торговли валютных пар и их торговые
характеристики. Партнёр определяется по метаданным `partner-id`, которые SDK
добавляет к каждому запросу, поэтому параметры не нужны.

```go
pairs, err := client.GetCurrencyPairs(ctx)
if err != nil {
    log.Fatalf("ошибка получения валютных пар: %v", err)
}

for _, p := range pairs {
    log.Printf("%s active=%v min_lot=%s min_trade_qty=%s valid_rate_percent=%d nbt_rate=%s tick_size=%s",
        p.Pair, p.IsActive, p.MinLot, p.MinTradeQuantity, p.ValidRatePercent, p.NbtRate, p.TickSize)
}
```

**Элемент `v1.CurrencyPair`:**

| Поле | Тип | Описание |
|------|-----|----------|
| `Pair` | `string` | Валютная пара, например `"USD/TJS"` |
| `MinLot` | `string` | Минимальный лот (десятичная строка) |
| `MinTradeQuantity` | `string` | Минимальный торгуемый объём (десятичная строка) |
| `ValidRatePercent` | `int32` | Допустимый коридор в % вокруг курса |
| `NbtRate` | `string` | Курс НБТ (десятичная строка) |
| `TickSize` | `string` | Шаг курса (десятичная строка, например `"0.010000"`): `LimitRate` должен быть ему кратен |
| `IsActive` | `bool` | Открыта ли пара для торговли |

Пару с `IsActive = false` торговать нельзя — Core отклонит ордер. `MinLot` и
`MinTradeQuantity` удобно проверять до вызова `SubmitOrder`, а `ValidRatePercent`
задаёт, насколько `LimitRate` может отклоняться от курса, чтобы ордер был принят.

`TickSize` — шаг курса пары: `LimitRate` должен делиться на него без остатка,
иначе Core отклонит ордер с причиной `limitRate должен быть кратен шагу курса …`.
Шаг задаётся для каждой пары отдельно (например, `0.01` для USD/TJS и EUR/TJS,
`0.0001` для RUB/TJS; по умолчанию `0.0001`) и может меняться администратором —
новое значение действует для новых ордеров примерно через 2 минуты. Поэтому
берите шаг из `GetCurrencyPairs`, а не зашивайте в код, и округляйте курс клиента
до шага до вызова `SubmitOrder`. Уже стоящие в стакане ордера смена шага не
затрагивает.

> **Новое поле.** `TickSize` (`tick_size = 7` в proto) добавлено без изменения
> остальных полей: старая версия SDK просто не видит его, но ордер с курсом не по
> шагу Core отклонит независимо от версии SDK.

> **Переименование поля.** Раньше это поле называлось `NbtAvgRate`
> (`nbt_avg_rate` в proto). Теперь — `NbtRate` (`nbt_rate`): это курс НБТ, а не
> усреднённое значение. Номер поля в proto (`5`) и тип не изменились, поэтому
> совместимость на уровне протокола сохранена — обновить нужно только код,
> который читал `NbtAvgRate`.

## Подписка на события ордеров — SubscribeOrderEvents

Серверный стрим: получает изменения статусов ордеров в реальном времени.
При получении события SDK обновляет локальную БД и вызывает ваш обработчик.

```go
func handleOrderEvent(event *v1.OrderEvent) {
    log.Printf("СОБЫТИЕ: ref_id=%d type=%d ts=%s remaining=%s",
        event.RefId, event.EventType, event.EventTimestamp, event.RemainingQuantity)

    // Если событие — отмена или истечение срока, нужно вернуть средства.
    if amount, release := event.GetReleaseAmount(); release {
        log.Printf("освободить средства: %s", amount)
    }
}

// Запускайте в отдельной горутине — вызов блокирующий.
go func() {
    err := client.SubscribeOrderEvents(ctx, partnerId, handleOrderEvent)
    if err != nil && ctx.Err() == nil {
        log.Printf("подписка завершилась с ошибкой: %v", err)
    }
}()
```

**Поведение переподключения:** стрим автоматически переоткрывается при временных
ошибках (`Unavailable`, `ResourceExhausted`) и чистом `EOF` от сервера, с задержкой
backoff между попытками. Счётчик неудач **сбрасывается при каждом успешном
получении сообщения**, поэтому работающая подписка переживает сколько угодно
переподключений. Метод возвращает управление только когда:

- контекст `ctx` отменён;
- ошибка не подлежит повтору;
- исчерпано `maxRetries` подряд неудачных попыток переподключения.

`OrderEvent.GetReleaseAmount()` удобно использовать для возврата средств: он
возвращает `(остаток, true)` для статусов `Expired`, `ExpiredPartially`,
`Cancelled`, `CancelledPartially` и `Failed` (последний приходит только от
`ReconcileOrders` — для ордера, который так и не дошёл до Core).

**Событие может не дойти.** Core отправляет событие один раз, только в открытый
стрим. Если стрим в этот момент был оборван (рестарт приложения, деплой Core,
сеть), ордер у вас останется «живым». Его закроет
[`ReconcileOrders`](#сверка-с-core--reconcileorders) и вызовет тот же
обработчик.

**Отмена не по вашей инициативе.** Событие `Cancelled` / `CancelledPartially`
может прийти и без вызова `CancelOrder`: если партнёра деактивировали на стороне
FX, Core в течение пары минут отменяет все его ордера, лежащие в стакане, и
присылает по событию на каждый. Обрабатывать их нужно так же, как любую отмену —
вернуть средства по `GetReleaseAmount()`. Сделки, совершённые до отмены, остаются
в силе и рассчитываются как обычно.

**Один стрим на SDK-ключ, и что его закрывает.** Правила одинаковы для
`SubscribeOrderEvents` и `SubscribeTrades`:

| Код gRPC | Причина | Что делать |
|----------|---------|------------|
| `Aborted` | Тем же SDK-ключом открыт более новый стрим. Core держит один стрим каждого вида на ключ и закрывает прежний | Не запускать два экземпляра на одном ключе — выпустите отдельный ключ на каждый |
| `Unauthenticated` | Ключ отозван. Открытый стрим закрывается в течение нескольких минут после отзыва | Обратиться к администратору FX; переподключение с тем же ключом не поможет |

Обе ошибки **не повторяются**: подписка возвращает их вызывающему коду. Не
глушите их — без стрима не приходят ни события, ни сделки. В структуре на
`errgroup` из [полного примера](#полный-пример) приложение при этом
останавливается, что и является правильной реакцией.

## Подписка на сделки — SubscribeTrades

Двунаправленный стрим, реализующий полный цикл расчёта по сделке. Для каждого
события Core SDK:

1. Находит родительский ордер по `ref_id` (берёт `client_id`, `side`,
   `currency_pair`, `account`, конфигурацию комиссии).
2. Вставляет сделку в `client_trades`.
3. Подтверждает сделку Core (**ack** = «получено и сохранено»).
4. Обновляет ордер: уменьшает `remaining_quantity` и ставит новый статус.
5. Вызывает ваш обработчик для расчёта по счетам партнёра (дебет/кредит).

```go
func handleTrade(ctx context.Context, ev *v1.TradeEvent) error {
    // ev.Settlement и ev.Fee уже вычислены SDK.
    log.Printf("СДЕЛКА: id=%d order=%d filled=%s rate=%s settlement=%s fee=%s pair=%s",
        ev.TradeId, ev.OrderId, ev.FilledQuantity, ev.ExecutionRate,
        ev.Settlement, ev.Fee, ev.CurrencyPair)

    // Перемещение средств по счетам партнёра.
    // ВАЖНО: операция ДОЛЖНА быть идемпотентной — одна и та же сделка
    // (trade_id, order_id, trading_day) может прийти повторно.
    return moveFunds(ctx, ev.Account["debit_account"],
        ev.Account["credit_account"], ev.Settlement, ev.Fee)
}

go func() {
    err := client.SubscribeTrades(ctx, handleTrade)
    if err != nil && ctx.Err() == nil {
        log.Printf("подписка на сделки завершилась с ошибкой: %v", err)
    }
}()
```

**Разделение состояний** (критично для денежных операций):

- **Получено и сохранено** — сделка надёжно записана в БД. Только после этого
  отправляется ack в Core. Если сохранить не удалось, ack не отправляется и
  Core доставит сделку повторно.
- **Рассчитано (settled)** — обработчик партнёра успешно выполнил перемещение
  средств. Отслеживается отдельно в колонке `settled`. Если обработчик вернул
  ошибку, сделка остаётся `settled = FALSE` с записанной ошибкой, и её повторит
  `RetryUnsettled`.

> **Подтверждение (ack) — как его принимает Core.** SDK делает всё нужное сам;
> это важно, только если вы пишете собственный клиент. Core принимает ack лишь
> по сделке, которую он отправил **в этот же стрим**, с тем же `trading_day` и
> той же стороной, и только один раз. Ack по незнакомой сделке, после
> переподключения в другой стрим или повторный — молча игнорируется. Стрим,
> который шлёт больше 50 сообщений в секунду (с запасом на всплеск в 200),
> теряет лишние сообщения, а при систематическом превышении закрывается с
> `ResourceExhausted`.

> **Требование идемпотентности.** Обработчик `TradeEventHandler` ДОЛЖЕН быть
> идемпотентным. Одна и та же сделка может быть представлена более одного раза —
> при повторной доставке после переподключения или при повторе после сбоя.
> Перемещение средств должно становиться no-op, если оно уже было применено
> для этой сделки.

Поля `TradeEvent` (наиболее важные):

| Поле | Описание |
|------|----------|
| `TradeId`, `OrderId` | Идентификаторы сделки и ордера в Core |
| `TradingDay` | День сделки `YYYY-MM-DD` |
| `FilledQuantity` | Исполненный объём в базовой валюте |
| `ExecutionRate` | Курс исполнения |
| `Side` | Направление (`Buy` / `Sell`) |
| `TradeType` | Тип сделки: кто стоял по обе стороны (см. ниже) |
| `Account` | JSONB-счета из родительского ордера (`map[string]string`) |
| `FeeConfig` | JSONB-конфигурация комиссии |
| `Settlement` | Итоговая сумма расчёта (`decimal.Decimal`), уже вычислена |
| `Fee` | Комиссия (`decimal.Decimal`), уже вычислена |

**Тип сделки — `TradeType`.** Core присылает его в поле `trade_type`
(`TradeResponse`, тег 12); SDK переносит значение в `TradeEvent.TradeType`,
`Trade.TradeType` и сохраняет в колонку `client_trades.trade_type`:

| Константа | Значение | Описание |
|-----------|----------|----------|
| `v1.SamePartner` | 1 | Один партнёр с обеих сторон, казначейства нет (Retail ↔ Retail) |
| `v1.SamePartnerTreasury` | 2 | Один партнёр, и одна из сторон — Treasury |
| `v1.CrossPartner` | 3 | Разные партнёры, сегменты любые |

`0` означает, что тип не известен: сделка сохранена до появления колонки или
пришла от Core, который поле ещё не присылает.

**Расчёт `Settlement` и `Fee`** (выполняется методом `TradeEvent.Cal()` внутри SDK):

```
m   = filled_quantity * execution_rate
fee = m * fee_config["fixed"] / 100          (комиссия в процентах)

Settlement = m + fee   (если Side == Buy)
Settlement = m - fee   (если Side == Sell)
```

Все результаты округляются до 6 знаков после запятой.

## Повторная обработка незакрытых сделок — RetryUnsettled

Переигрывает обработчик расчёта для всех сделок, которые сохранены, но ещё не
рассчитаны (`settled = FALSE`) — например, обработчик упал, или процесс
завершился после ack, но до расчёта.

Источник истины для «деньги ещё нужно переместить» — это локальный флаг
`settled`, а не повторная доставка от Core. Поэтому `RetryUnsettled` гарантирует,
что неудавшийся расчёт будет в итоге повторён даже на здоровом, никогда не
переподключающемся стриме.

**Вызывайте при старте приложения и по таймеру:**

```go
// При старте.
if err := client.RetryUnsettled(ctx, handleTrade); err != nil {
    log.Printf("retry unsettled (старт): %v", err)
}

// По таймеру.
go func() {
    t := time.NewTicker(time.Minute)
    defer t.Stop()
    for {
        select {
        case <-ctx.Done():
            return
        case <-t.C:
            if err := client.RetryUnsettled(ctx, handleTrade); err != nil {
                log.Printf("retry unsettled: %v", err)
            }
        }
    }
}()
```

> Обработчик так же ДОЛЖЕН быть идемпотентным — сделка может быть представлена
> ему повторно.

## Сверка с Core — ReconcileOrders

`ReconcileOrders` — **единственная** сверка SDK. Она находит ордера, которые у
вас всё ещё `Pending` или `FilledPartially`, хотя их срок жизни давно прошёл,
спрашивает Core, чем они закончились, и приводит в порядок **и сделки, и сам
ордер** в одной транзакции.

Зачем: Core присылает сделку и событие ордера **один раз** и только в открытый
стрим. Если в этот момент связи не было (рестарт приложения, деплой Core, сеть),
сделка не проведена у клиента, а ордер остаётся «живым» с заблокированными
средствами.

```go
res, err := client.ReconcileOrders(ctx, &v1.ReconcileOrdersParams{
    PartnerId: partnerId,
}, handleTrade, handleOrderEvent) // те же обработчики, что у стримов
if err != nil {
    log.Printf("сверка: %v", err)
}
log.Printf("проверено=%d сделок_добавлено=%d закрыто=%d снято_блокировок=%d",
    res.Checked, res.TradesAdded, res.Closed, res.Released)
```

Запускайте **при старте приложения и раз в час** (см. [полный пример](#полный-пример)).

### Как работает

Берутся ордера партнёра, поданные больше `OlderThan` назад (по умолчанию
25 часов — больше срока жизни любого ордера, значит в Core он уже закрыт), и
при этом:

- ещё «живые» — `Pending` / `FilledPartially`;
- **или** уже закрытые, но **сделок у них меньше, чем исполнено**:
  `количество − остаток` больше суммы их сделок в `client_trades`. Так бывает,
  когда событие ордера дошло, а сделки — нет. Такому ордеру сверка только
  догружает сделки: статус и остаток уже от Core, блокировка уже снята. Core опрашивается пачками по 500
(`GetOrderStatuses`, по ключам `order_day` + `ref_id`) и отдаёт статус, остаток
и все сделки ордера. Для каждого ордера, в одной транзакции:

1. **Недостающие сделки** сохраняются в `client_trades` так же, как их
   сохраняет стрим, и уменьшают остаток ордера.
2. **Остаток сравнивается с Core:**

| Ваш остаток против Core | Что это значит | Что делает SDK |
|---|---|---|
| равен | событие ордера к вам не доходило, блокировку не снимали | ставит статус Core; для `Expired`, `ExpiredPartially`, `Cancelled`, `CancelledPartially`, `Failed` вызывает `handleOrderEvent` с остатком Core |
| меньше | событие дошло и блокировку уже сняли, а потом пришла запоздавшая сделка и вычла объём ещё раз | ставит статус и остаток Core, **блокировку не снимает** |
| больше | Core ещё не отдал все сделки (расчёт по ним записывается) | ничего не меняет, повторит при следующем запуске |

3. **Ордера нет в Core** — он туда не дошёл: статус `Failed`, `cause` =
   «ордер не дошёл до Core», `handleOrderEvent` получает весь локальный остаток.

После коммита для каждой нерассчитанной сделки вызывается `handleTrade`
(проводка денег), затем `handleOrderEvent`, если блокировку нужно снять. Ордер,
который тем временем закрыло событие из стрима, пропускается.

### Сделка не меняет закрытый ордер

Когда приходит сделка, SDK уменьшает остаток ордера и ставит статус
`FilledPartially`, или `Filled`, если ордер исполнен полностью. Закрывающие
статусы (истёк, отменён) приходят **только событием ордера**.

Если ордер у вас **уже закрыт** (`Filled`, `Cancelled`, `Expired`,
`CancelledPartially`, `ExpiredPartially`), сделка сохраняется в `client_trades`
и передаётся в `handleTrade`, но **статус и остаток ордера не меняет**: они
пришли из Core и эту сделку уже учитывают. Это важно, потому что порядок
прихода не гарантирован. Например, у рыночного ордера событие «остаток
отменён» отправляется сразу, а сделки проходят расчёт и приходят позже.

| Порядок прихода (рыночный ордер 25: сделки 8 и 10, остаток 7 отменён) | Остаток у вас |
|---|---|
| сделка 8 → сделка 10 → событие | 17 → 7 → **7** |
| событие → сделка 8 → сделка 10 | 7 → 7 → **7** |
| сделка 10 → событие → сделка 8 | 15 → 7 → **7** |

### Все случаи

Пример везде один: ордер на покупку **100 USD**. «У вас» — строка в
`client_orders` до сверки, «Core» — что ответил `GetOrderStatuses`.
`handleTrade` вызывается для каждой сделки, которой у вас не было;
`handleOrderEvent` — когда нужно снять блокировку.

| # | У вас: статус / остаток | Core: статус / остаток | Сделки у вас | Как так получилось | Результат у вас | `handleTrade` | `handleOrderEvent` |
|---|---|---|---|---|---|---|---|
| 1 | Pending / 100 | Expired / 100 | нет, и не было | потерялось событие об истечении | Expired / 100 | — | ✅ снять 100 |
| 2 | Pending / 100 | Cancelled / 100 | нет, и не было | потерялось событие об отмене (Core отменяет ордера отключённого партнёра) | Cancelled / 100 | — | ✅ снять 100 |
| 3 | Pending / 100 | Failed / 100 | нет, и не было | потерялся ответ на `SubmitOrder`, Core пометил ордер Failed | Failed / 100 | — | ✅ снять 100 |
| 4 | Pending / 100 | ордера нет | нет | ордер не дошёл до Core (сбой до отправки) | Failed / 100, `cause` = «ордер не дошёл до Core» | — | ✅ снять 100 |
| 5 | Pending / 100 | Filled / 0, сделки 60 + 40 | нет обеих | потерялись обе сделки | Filled / 0 | ✅ 60 и 40 | — (всё исполнено) |
| 6 | Pending / 100 | ExpiredPartially / 70, сделка 30 | нет | потерялись и сделка, и событие | ExpiredPartially / 70 | ✅ 30 | ✅ снять 70 |
| 7 | FilledPartially / 60 | Filled / 0, сделки 40 + 60 | есть 40, нет 60 | потерялась последняя сделка | Filled / 0 | ✅ 60 | — |
| 8 | FilledPartially / 0 | Filled / 0, сделки 40 + 60 | обе есть | сделки пришли не по порядку: последняя раньше, статус откатился | Filled / 0 | — | — |
| 9 | FilledPartially / 80 | ExpiredPartially / 50, сделки 20 + 30 | есть 20, нет 30 | потерялись вторая сделка и событие | ExpiredPartially / 50 | ✅ 30 | ✅ снять 50 |
| 10 | FilledPartially / 80 | ExpiredPartially / 80, сделка 20 | есть | сделка дошла, событие об истечении потерялось | ExpiredPartially / 80 | — | ✅ снять 80 |
| 11 | FilledPartially / **60** | ExpiredPartially / **80**, сделка 20 | есть | событие **дошло** (блокировка 80 уже снята), потом сделка пришла с опозданием и вычла 20 ещё раз | ExpiredPartially / 80 | — | ❌ **не снимать** — уже снято |
| 12 | Pending / 100 | Pending / 100 | нет | в Core ещё не отработало истечение | без изменений | — | — (повтор в следующий час) |
| 13 | Pending / 100 | Filled / 0, но отдана только сделка 40 | нет | Core ещё записывает расчёт по второй сделке | FilledPartially / 60 (сохранена сделка 40) | ✅ 40 | — (повтор в следующий час) |
| 14 | CancelledPartially / 70 | CancelledPartially / 70, сделка 30 | нет | рыночный ордер: событие «остаток 70 отменён» дошло, сделка — нет | без изменений, сделка сохранена | ✅ 30 | — (блокировку сняло событие) |
| 15 | Expired / 100 | — | нет, и не было | закрыт событием, ничего не исполнялось | не проверяется | — | — |
| 16 | Filled / 0 | — | все | всё дошло | не проверяется | — | — |

Как SDK различает случаи 10 и 11: после догрузки сделок сравнивается остаток.

- **Равен остатку Core** (случаи 1–3, 5–10) — событие к вам не применялось,
  блокировку ещё не снимали: снять, если статус Core — `Expired`,
  `ExpiredPartially`, `Cancelled`, `CancelledPartially` или `Failed`.
- **Меньше остатка Core** (случай 11) — событие применялось и записало остаток
  Core, а запоздавшая сделка вычла свой объём второй раз. Блокировка уже снята:
  SDK только исправляет статус и остаток.
- **Больше остатка Core** (случай 13) — Core знает об исполнении, но ещё не
  отдал сделку. SDK сохраняет то, что пришло, и ждёт следующего запуска.

**Что сверка не трогает:**

| Ордер | Почему |
|---|---|
| Подан меньше 25 часов назад | может быть ещё жив; проверится, когда станет старше |
| Уже закрыт у вас и все его сделки на месте | всё уже обработано стримом |
| Закрыт событием из стрима, пока шла сверка | строка блокируется и перепроверяется в транзакции — ордер пропускается |
| Другого партнёра | сверка идёт по `PartnerId` |
| Старше `LookbackDays` (7 дней) | слишком старый; при необходимости увеличьте параметр |
| `Rejected` / `Duplicate` | Core такие ордера не хранит — сверять нечего |

**Повторный запуск безопасен:** сделки не сохраняются дважды (`ON CONFLICT`),
закрытый ордер не выбирается снова, поэтому блокировка не снимается второй раз.

Параметры `ReconcileOrdersParams`:

| Поле | По умолчанию | Смысл |
|------|--------------|-------|
| `PartnerId` | — (обязателен) | Чьи ордера сверять |
| `OlderThan` | 25 ч | Сверять ордера, поданные раньше этого |
| `LookbackDays` | 7 | Сколько дней ордеров просматривать, сегодня включительно |

Поля `ReconcileOrdersResult`:

| Поле | Описание |
|------|----------|
| `Checked` | Сколько ордеров спросили у Core |
| `TradesAdded` | Сколько сделок не было у вас и сохранено |
| `Closed` | Сколько ордеров закрыто статусом Core |
| `Released` | Сколько раз вызван `handleOrderEvent` для снятия блокировки |
| `Corrected` | Закрыто без снятия: блокировку уже сняли раньше |
| `Completed` | Ордер уже был закрыт, но не хватало сделок — сделки догружены, больше ничего не менялось |
| `Lost` | Ордеров не было в Core — помечены `Failed` |
| `StillLive` | В Core ордер ещё живой (не отработало истечение) — повтор позже |
| `Behind` | Core отдал не все сделки — повтор позже |

Метод `GetOrderStatuses` появился в Core вместе с этой версией SDK: против
старого Core вызов вернёт `Unimplemented`.

> **Прежние сверки удалены.** `Reconcile`, `ReconcileDiff`, `ReconcileRepair` и
> `RecoverTrades` больше не существуют — их заменяет `ReconcileOrders`. Таблица
> `reconciliations` не используется; в существующей базе её можно удалить
> (`DROP TABLE IF EXISTS reconciliations;`). `GetTrades` остаётся для чтения
> сделок Core за день.

## Справочник типов и констант

### Направление ордера — `Side`

```go
v1.Buy  // 1 — покупка
v1.Sell // 2 — продажа
```

### Сегмент рынка — `Segment`

```go
v1.Retail    // 1 — розница
v1.Corporate // 2 — корпоративный
v1.Treasury  // 3 — казначейство
```

Нулевое значение `Segment` не является сегментом ордера — это значение по
умолчанию для `CounterpartySegment`:

```go
v1.AnyCounterparty // 0 — контрагент из любого сегмента
```

### Тип ордера — `OrderType`

```go
v1.LimitOrder  // 1 — лимитный (по умолчанию, если поле не задано)
v1.MarketOrder // 2 — рыночный: без LimitRate, остаток отменяется
```

### Тип сделки — `TradeType`

```go
v1.SamePartner         // 1 — один партнёр, без казначейства (Retail ↔ Retail)
v1.SamePartnerTreasury // 2 — один партнёр, одна из сторон Treasury
v1.CrossPartner        // 3 — разные партнёры, сегменты любые
```

### Статус ордера — `OrderStatus`

| Константа | Значение | Описание |
|-----------|----------|----------|
| `Unknown` | 0 | Неизвестно |
| `Pending` | 1 | В ожидании |
| `FilledPartially` | 2 | Частично исполнен |
| `Filled` | 3 | Полностью исполнен |
| `Cancelled` | 4 | Отменён |
| `Expired` | 5 | Истёк срок |
| `Failed` | 6 | Ошибка |
| `CancelledPartially` | 7 | Частично отменён |
| `ExpiredPartially` | 8 | Частично истёк |
| `Rejected` | 9 | Отклонён |
| `Duplicate` | 10 | Дубликат |

### Денежные значения

Все количества, курсы и суммы — **строки** для произвольной десятичной точности:
`"1000.00"`, `"9.3100"`. В `TradeEvent` поля `Settlement` и `Fee` имеют тип
`decimal.Decimal` (`github.com/govalues/decimal`).

## Обработка ошибок

Предопределённые ошибки SDK (сравнивайте через `errors.Is`):

| Ошибка | Когда возникает |
|--------|-----------------|
| `v1.ErrDuplicateOrder` | Дубликат ордера в пределах 1 минуты |
| `v1.ErrClientIDRequired` | Не указан `client_id` |
| `v1.ErrPartnerIDRequired` | Не указан `partner_id` |
| `v1.ErrLimitRateRequired` | Лимитный ордер без `LimitRate` |
| `v1.ErrInvalidOrderType` | `OrderType` не `LimitOrder` и не `MarketOrder` |
| `v1.ErrInvalidCounterpartySegment` | `CounterpartySegment` не `AnyCounterparty` и не `Treasury` |
| `v1.ErrTreasuryCounterpartyOnly` | `CounterpartySegment = Treasury` задан для не-казначейского ордера |
| `v1.ErrDecimalPrecision` | В десятичном значении больше 6 знаков после запятой |
| `v1.ErrInvalidDay` | День не в формате `YYYY-MM-DD` |

```go
res, err := client.SubmitOrder(ctx, params)
switch {
case errors.Is(err, v1.ErrDuplicateOrder):
    // дубликат — обычно безопасно пропустить
case errors.Is(err, v1.ErrClientIDRequired):
    // ошибка валидации параметров
case err != nil:
    // сетевые/серверные ошибки (gRPC). Временные ошибки уже
    // повторены внутри SDK согласно WithMaxRetries.
default:
    // успех
}
```

Временные ошибки gRPC (`Unavailable`, `ResourceExhausted`) автоматически
повторяются для unary-вызовов и вызывают переподключение для стримов.

Ошибки gRPC, которые не повторяются и требуют действия:

| Код | Где | Что означает |
|-----|-----|--------------|
| `Unauthenticated` | любой вызов | Неверный или отозванный ключ, либо нет клиентского сертификата; для открытого стрима — ключ отозван |
| `PermissionDenied` | любой вызов | Клиентский сертификат выдан другому SDK-ключу, либо сегмент недоступен этому ключу |
| `Aborted` | стримы | Тем же ключом открыт более новый стрим |
| `InvalidArgument` | `GetTrades`, `GetOrderStatuses`, `FilterClientOrders`, `GetOrderBookDepth` | Неверные параметры запроса |

Отказ по содержимому ордера — не ошибка gRPC: `SubmitOrder` возвращает
`err == nil`, статус `Rejected` и причину в `Cause` (см.
[Отправка ордера](#отправка-ордера--submitorder)).

## Полный пример

Полный рабочий пример с подписками, отправкой, фильтрацией и отменой ордера
находится в [`go/example/main.go`](go/example/main.go). Запуск:

```bash
cd go && go run ./example \
    -target=fx-core.example.com:443 \
    -sdk-id=YOUR_SDK_ID \
    -api-key=YOUR_API_KEY \
    -partner-id=YOUR_PARTNER_ID \
    -dsn="postgres://user:pass@localhost:5432/fxdb?sslmode=disable" \
    -client-id=CLIENT_42 \
    -client-inn=123456789
```

Дополнительные флаги:

| Флаг | Назначение |
|------|-----------|
| `-insecure` | Незащищённое (plaintext) соединение — только для разработки |
| `-mTLS` | Предъявить клиентский сертификат (`-tls-cert`, `-tls-key`) |
| `-tls-ca` | CA для проверки сервера; пусто — системные корневые сертификаты |
| `-market` | Дополнительно отправить рыночный ордер |
| `-cancel` | Найти открытый ордер через `FilterClientOrders` и отменить его |

Без `-insecure` и `-mTLS` используется обычный TLS без клиентского сертификата.

Рекомендуемая структура продакшен-приложения (через `errgroup`):

```go
g, ctx := errgroup.WithContext(context.Background())
ctx, stop := signal.NotifyContext(ctx, os.Interrupt)
defer stop()

// 1. Подписка на события ордеров.
g.Go(func() error {
    return client.SubscribeOrderEvents(ctx, partnerId, handleOrderEvent)
})

// 2. Подписка на сделки.
g.Go(func() error {
    return client.SubscribeTrades(ctx, handleTrade)
})

// 3. Переигрывание незакрытых расчётов при старте и по таймеру.
g.Go(func() error {
    _ = client.RetryUnsettled(ctx, handleTrade)
    t := time.NewTicker(time.Minute)
    defer t.Stop()
    for {
        select {
        case <-ctx.Done():
            return ctx.Err()
        case <-t.C:
            _ = client.RetryUnsettled(ctx, handleTrade)
        }
    }
})

// 4. Сверка с Core: при старте и раз в час.
g.Go(func() error {
    reconcile := func() {
        if _, err := client.ReconcileOrders(ctx,
            &v1.ReconcileOrdersParams{PartnerId: partnerId}, handleTrade, handleOrderEvent); err != nil {
            log.Printf("сверка: %v", err)
        }
    }
    reconcile()
    t := time.NewTicker(time.Hour)
    defer t.Stop()
    for {
        select {
        case <-ctx.Done():
            return ctx.Err()
        case <-t.C:
            reconcile()
        }
    }
})

// ... бизнес-логика (SubmitOrder, CancelOrder, ...) ...

if err := g.Wait(); err != nil {
    log.Fatalln("завершение:", err)
}
```

## Чек-лист интеграции

- [ ] Создана схема БД из [`go/db.sql`](go/db.sql) (PostgreSQL + TimescaleDB).
- [ ] Получены `sdk_id` (36-символьный UUID), `api_key` и `partner_id`.
- [ ] DEV: подключение через `insecure` (без mTLS). PROD: настроен **mTLS**
      (клиентский сертификат + ключ + CA) через `WithDialOptions`.
- [ ] Запущены подписки `SubscribeOrderEvents` и `SubscribeTrades` в горутинах.
- [ ] На каждый экземпляр приложения — **свой SDK-ключ**: второй стрим на том же
      ключе закрывает первый с `Aborted`.
- [ ] Ошибки подписок `Aborted` и `Unauthenticated` не глушатся: приложение
      останавливается или поднимает алерт.
- [ ] `ClientINN` — от 9 до 12 цифр, `ClientId` — от 1 до 100 символов.
- [ ] Настроен `RetryUnsettled` при старте и по таймеру.
- [ ] `ReconcileOrders` запускается при старте и раз в час, с теми же
      обработчиками `handleTrade` и `handleOrderEvent`; алерт, если `Behind`
      или `StillLive` держатся несколько запусков подряд.
- [ ] Обработчик сделок `handleTrade` сделан **идемпотентным**.
- [ ] Реализован возврат средств по `OrderEvent.GetReleaseAmount()` — в том
      числе для отмен, которые инициировал Core (деактивация партнёра).
- [ ] Денежные значения передаются как строки с нужной точностью.
- [ ] Вызывается `client.Close()` при завершении.
